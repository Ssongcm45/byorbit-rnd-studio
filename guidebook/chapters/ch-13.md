# 자료 수집

지금까지는 내가 가진 파일을 넣었습니다. 이 장에서는 바깥에서 새 자료를 **가져오는** 방법을 봅니다. 이 기능은 이런 요청에서 시작했습니다.

> "논문이나 자료를 수집하는거야. 즉 크롤러와 공식 api를 통해 수집하는 것 두가지가 필요해"

요청대로 길은 두 갈래입니다. **공식 API**와 **크롤러**입니다.

### 두 갈래 길

![수집 흐름 — 두 갈래 길에서 자료함까지](i09-collect.png "출처: 송창민 작성")

- **공식 API** — 학술 데이터베이스가 "이렇게 물어보면 이렇게 답해 주겠다"고 열어 둔 창구입니다. 정해진 모양으로 답이 오므로 정확합니다.
- **크롤러** — API가 없는 공개 웹 목록(예: 기관 보도자료 게시판)을 프로그램이 대신 읽어 오는 것입니다. 크롤(crawl)은 "기어 다닌다"는 뜻입니다.

두 길로 모은 자료는 곧장 자료함에 들어가지 않습니다. 먼저 **수집함**에 쌓이고, 사람이 검토한 것만 자료함에 넣습니다. 11장의 라벨 검토와 같은 원칙입니다.

### 공식 API 출처

**API 키**는 "이 사람이 쓰는 것"임을 알리는 열쇠 글자입니다. 각 기관 누리집에서 신청해 받습니다. 키 발급 방법과 넣을 환경 변수 이름은 수집 화면의 **키 발급 안내**에 있습니다.

3. 검색창에 "apple pomace drying"을 넣고 검색합니다.
4. 결과가 **수집함**에 카드로 쌓이는 것을 봅니다.

### 키는 환경 변수로만

국내 출처를 쓰려면 키를 넣어야 합니다. 키는 설정 파일이 아니라 **환경 변수**에 넣습니다(8장). PowerShell에서 한 번만 하면 됩니다.

```powershell
[Environment]::SetEnvironmentVariable("BYORBIT_KCI_KEY", "발급받은키", "User")
```

넣은 뒤에는 start.bat으로 앱을 다시 켜야 키가 보입니다. 기관마다 신청 조건이 조금씩 다릅니다. ScienceON은 신청할 때 이 PC의 MAC 주소(네트워크 장치 번호)를 적어야 하고, NTIS는 내 정보에 소속 기관을 등록해야 신청할 수 있습니다. KIPRIS는 한 달에 1,000건까지 무료입니다. 수집 화면의 키 발급 안내에 기관별 순서가 있습니다. 키가 없는 출처는 흐리게 보이고, 빠진 환경 변수 이름을 알려 줍니다.

::: warn 주의
키 값을 메모장·설정 파일·메신저에 적어 두지 마세요. 이 앱도 키를 파일·데이터베이스·로그에 쓰지 않고, 오류 메시지에 키가 섞이면 `***`로 가립니다. 일부 기관 서버는 잘못된 키를 받으면 그 키를 오류 문구에 그대로 되돌려 주는데, 앱은 이것도 가려서 보여 줍니다.
:::

### 수집함에서 검토하기

수집함에서는 카드마다 제목·저자·연도·출처와 함께 배지가 붙습니다. **OA** 배지는 오픈 액세스(누구나 무료로 볼 수 있는 논문), **PDF** 배지는 원문 PDF를 받을 수 있다는 뜻입니다.

![수집함 — 결과 카드(실제 검색 결과 44건 중 앞부분)](s09a-inbox-cards.png "출처: R&D Studio V0.5 화면(예시 데이터)")

![저장 검색 — 하루마다 자동으로 다시 찾는 설정](s09b-inbox-saved.png "출처: R&D Studio V0.5 화면(예시 데이터)")

- 같은 논문이 여러 출처에서 오면 DOI → 출처 번호 → 제목 순으로 비교해 **하나로 합칩니다**.
- 수집함 위쪽의 탭(새 항목·보관(나중에)·거절·자료함에 넣음)으로 상태별로 나눠 봅니다. "오픈 액세스만"을 켜면 무료 원문이 있는 것만 보입니다.
- 검토할 때는 제목과 학술지·연도를 먼저 보고, **초록 보기**를 펼쳐 내 주제와 맞는지 확인한 뒤, 맞는 것만 넣습니다. 애매하면 **나중에**로 보관해 둡니다.
- **자료함에 넣기**를 누르면, 오픈 액세스면 원문 PDF를, 아니면 서지와 초록만 넣습니다. 유료 논문 원문을 몰래 받지 않습니다.
- 한 출처가 실패해도 다른 출처의 결과는 그대로 들어옵니다. 이 화면을 찍을 때도 Europe PMC는 시간 초과, Semantic Scholar는 "잠시 막힘" 오류가 났지만 OpenAlex·Crossref 결과는 정상으로 쌓였습니다. 실패한 출처는 잠시 뒤 다시 검색하면 됩니다(저장 검색으로 다시 돌렸을 때 Europe PMC는 정상으로 받았습니다).
- 검색을 **저장**하면 앱이 켜져 있는 동안 정한 주기로 새 자료를 찾아 수집함에 넣어 줍니다.

## 자료를 모으는 네 가지 방법

바깥 자료를 가져오는 방법은 크게 네 가지입니다. **공식 API**, **직접 만든 크롤러**, **Playwright** (브라우저 자동화), **Apify** (클라우드 크롤링)입니다. 이 앱은 앞의 셋을 쓰고(Playwright는 라이브러리로만), 넷째는 선택으로 붙여 두었습니다. 하나씩 보고, 마지막에 언제 무엇을 쓸지 정리합니다.

![자료를 모으는 네 가지 방법과 고르는 순서](i17-crawl-methods.png "출처: 송창민 작성")

### 모두가 지켜야 할 것

어떤 방법이든 남의 누리집과 데이터베이스를 쓰는 일입니다. 다섯 가지를 먼저 지킵니다.

1. **robots.txt** — 누리집이 "로봇은 여기까지만 오세요"라고 적어 둔 파일입니다. 막힌 주소는 가지 않습니다.
2. **이용약관** — 자동 수집을 허락하는지, 영리 목적을 막는지 읽습니다. 확인하지 못한 곳은 꺼 둡니다.
3. **저작권** — 제목·서지·초록 정도를 기록하고, 원문은 공개(오픈 액세스·공공누리)된 것만 받습니다.
4. **개인정보** — 사람 이름·연락처를 모으는 것이 목적이 되면 안 됩니다. 이 앱은 자기 소개(User-Agent)에도 이메일을 넣지 않습니다.
5. **요청 간격** — 서버에 부담을 주지 않게 천천히 갑니다. 이 앱은 같은 호스트에 최소 3초, 기본 사이트는 5초 간격이고, robots.txt의 Crawl-delay가 더 길면 그것을 따릅니다.

**User-Agent**는 프로그램이 누리집에 "나는 누구다"라고 밝히는 이름표입니다. 이 앱은 `RD-Studio/0.5 (local research tool)`라는 일반 이름을 씁니다.

### 방법 1. 공식 API — 정해진 창구에 묻기

**비유:** 도서관 안내 데스크에 "이런 책 있나요?"라고 묻는 것입니다. 데스크는 정해진 양식으로 답해 줍니다.

**동작:** 앱이 검색어를 정해진 주소 꼴로 보내면, 데이터베이스가 정리된 데이터(JSON·XML)로 답합니다. 앱은 출처마다 다른 답을 같은 모양(5장의 `Item`)으로 맞춰 수집함에 넣습니다. 예를 들어 OpenAlex에 보내는 요청은 이런 모양입니다(일부 생략).

```text
https://api.openalex.org/works?search=apple+pomace+drying&per_page=25
```

PC 밖으로 나가는 것은 이 주소에 담긴 **검색어**뿐입니다. 키가 필요한 출처는 그 출처의 키가 함께 갑니다.

- **장점:** 데이터가 정확하고 구조가 일정합니다. 허락된 길이라 법·약관 걱정이 가장 적습니다.
- **단점:** API가 있는 곳만 됩니다. 키 발급이 번거롭고, 호출 한도가 있습니다(OpenAlex는 키 없이 하루 약 100회).
- **비용:** 이 앱이 쓰는 학술 API는 무료입니다. 단 KIPRIS처럼 무료 한도를 넘으면 유료인 곳이 있습니다.
- **언제:** 공식 API가 있으면 언제나 이것이 먼저입니다.
- **이 앱에서:** **자료 수집** 화면에서 출처 묶음에 체크하고 검색합니다. 해외 학술 4곳(OpenAlex·Crossref·Europe PMC·Semantic Scholar)은 키가 필요 없고, 국내 7곳(KCI·ScienceON·NTIS·KIPRIS·공공데이터 3종)은 환경 변수로 키를 넣습니다. 앱은 출처마다 요청 간격을 두고, 오류 메시지에 키가 섞이면 `***`로 가립니다.

### 방법 2. 직접 만든 크롤러 — 공개 목록을 대신 읽기

**비유:** 게시판을 한 쪽씩 넘겨 보며 제목을 수첩에 옮겨 적는 사람입니다. 다만 출입 규칙(robots.txt)을 먼저 확인하고, 천천히 넘깁니다.

**동작:** 시작 주소의 HTML을 받아 링크와 제목·날짜를 읽고, 허용한 경로 안의 상세 페이지만 따라갑니다. 이 앱의 "기본(HTTP)" 방식이 이것입니다. 원리를 보여 주는 예시는 아래와 같습니다(이 앱의 실제 코드가 아니라 원리를 보여 주는 예시입니다).

```python
# 원리를 보여 주는 예시 — robots.txt 확인 → 천천히 받기 → 링크 읽기
import time, urllib.robotparser, urllib.request
from html.parser import HTMLParser
rp = urllib.robotparser.RobotFileParser("https://example.org/robots.txt"); rp.read()
url = "https://example.org/board/list"
if rp.can_fetch("RD-Studio", url):
    html = urllib.request.urlopen(url).read().decode("utf-8")
    class Links(HTMLParser):
        def handle_starttag(self, tag, attrs):
            if tag == "a": print(dict(attrs).get("href"))
    Links().feed(html); time.sleep(3)   # 다음 요청 전 3초 쉬기
```

- **장점:** 설치가 필요 없고 빠릅니다. API가 없는 공공기관 보도자료·보고서 목록도 읽습니다.
- **단점:** 누리집 모양이 바뀌면 고쳐야 합니다. 자바스크립트로 그리는 목록은 못 읽습니다. 로그인이 필요한 곳은 넣지 않습니다.
- **비용:** 없음.
- **언제:** API가 없고, 서버가 목록을 HTML로 그려 주는 공개 페이지.
- **이 앱에서:** 기본 사이트 5곳 중 3곳이 켜져 있습니다(농촌진흥청 보도자료, 국립농업과학원·국립원예특작과학원 시험연구보고서). 한국식품연구원 2곳은 이용약관을 확인하지 못해 꺼 두었습니다. robots.txt와 약관은 2026-11-25에 확인했고, 그날 "부산물"로 농촌진흥청 보도자료를 6쪽 읽어 10건을 찾았습니다. 앱은 RFC 9309(robots.txt 표준) 규칙으로 판정하고, robots.txt를 못 받으면(401·403·5xx) 그 호스트를 통째로 건너뜁니다. 한 번에 기본 10쪽(최대 30쪽), 깊이 1(최대 2)까지만 갑니다.

### 방법 3. Playwright — 브라우저를 프로그램이 조종하기

**비유:** 사람 대신 브라우저 앞에 앉은 로봇입니다. 페이지를 열고, 자바스크립트가 목록을 다 그릴 때까지 기다렸다가 읽습니다.

Playwright는 마이크로소프트가 만든 브라우저 자동화 도구입니다(오픈소스, Apache-2.0). 쓰는 길이 두 가지라 구분해야 합니다.

**① 라이브러리 — 이 앱의 "브라우저(Chrome)" 방식**

정해진 코드가 정해진 규칙으로 브라우저를 씁니다. 사람이 정한 사이트만, 정한 순서로 돕니다.

- 이 PC에 설치된 Chrome을 화면 없이(**헤드리스**) 띄웁니다. 설치는 `install-browser.bat` 한 번입니다.
- http·https가 아닌 주소(`file://` 같은 PC 파일 주소 포함)로는 이동하지 않고, 페이지 안의 그런 요청도 모두 끊습니다. 이미지·글꼴·영상은 받지 않습니다.
- 기본 방식과 똑같이 robots.txt·간격·쪽수 규칙을 지킵니다.
- **장점:** 자바스크립트로 그리는 목록도 읽습니다. **단점:** 느립니다(2026-11-25 시험에서 5쪽에 약 27~49초). 설치가 필요합니다. **비용:** 없음.

**② Playwright MCP — AI가 직접 브라우저를 다루는 통로(이 앱 안에서는 쓰지 않음)**

**MCP 서버**는 AI에게 도구를 주는 작은 프로그램입니다(5장). Playwright MCP는 AI가 브라우저를 직접 열고, 누르고, 읽게 해 줍니다. 공식 이름은 `@playwright/mcp`이고, Claude Code에는 이렇게 붙입니다(공식 README, 2026-11-26 확인).

```powershell
claude mcp add playwright npx @playwright/mcp@latest
```

라이브러리와의 차이는 **누가 운전하느냐**입니다. 라이브러리는 코드가 정한 길만 가고, MCP는 AI가 그때그때 판단해 클릭합니다. 그래서 MCP는 처음 보는 누리집의 구조를 살펴보거나, 버튼을 눌러야 나오는 자료를 한 번 모아 볼 때 좋습니다. 매일 같은 일을 반복하는 데는 라이브러리가 낫습니다.

이 앱은 자기 AI에 브라우저 MCP를 **일부러 붙이지 않았습니다.** 브라우저는 `file://` 주소로 PC 안의 파일을 열 수 있어서, AI가 기밀 원본을 가림 없이 읽는 길이 될 수 있기 때문입니다. 최신 Playwright MCP는 기본으로 `file://` 이동을 막지만, 옵션으로 풀 수 있고 공식 문서도 "보안 경계가 아니다"라고 밝힙니다. 그래서 이 앱은 AI에게 앱의 도구 7개만 줍니다(8장).

::: warn Playwright MCP를 내 Claude Code에서 쓸 때
기밀 자료가 없는 **새 폴더**에서 Claude Code를 열고 붙입니다. AI가 연 페이지와 모은 내용을 직접 검토하고, 누리집의 robots.txt와 이용약관을 지키게 요청합니다. 로그인이 필요한 사이트에 내 계정으로 들어가게 하지 않습니다.
:::

예를 들어 이렇게 요청합니다. "농촌진흥청 보도자료 목록 페이지 구조를 살펴보고, 제목·날짜·상세 주소가 어디에 있는지 알려 줘. robots.txt를 먼저 확인하고, 3쪽까지만 보고, 페이지 사이에 몇 초씩 쉬어 줘. 모은 내용은 표로만 보여 주고 파일로 저장하지 마." 이렇게 알아낸 구조를 이 앱의 **사이트 추가** 설정(허용 경로·링크 꼴)에 옮겨 적으면, 그다음부터는 앱의 크롤러가 규칙대로 반복합니다.

### 방법 4. Apify — 클라우드에 맡기는 크롤링

**비유:** 크롤링 전문 업체에 맡기는 것입니다. 내 PC 대신 업체의 서버가 브라우저를 돌리고, 결과만 받아 옵니다.

**동작:** 이 앱은 Apify의 Website Content Crawler 액터(미리 만든 크롤링 프로그램)를 실행시키고, 끝날 때까지 상태를 물어본 뒤, 결과를 받아 옵니다. 받은 페이지는 이 PC가 robots.txt·허용 경로·쪽수 규칙으로 **다시 거릅니다.**

- **장점:** 내 PC에서 막히거나 브라우저를 깔 수 없을 때도 되고, 대량 수집과 관리를 맡길 수 있습니다.
- **단점:** 사이트 주소와 크롤 설정이 Apify로 나갑니다(검색어는 보내지 않음). Apify는 Crawl-delay를 지원하지 않아, 앱이 한 번에 한 쪽씩만 요청하도록 설정합니다.
- **비용:** 유료(크레딧)입니다. 이 앱은 실행마다 비용 상한을 걸고 기본값은 0.5 USD입니다(앱 설정값이지 Apify 요금이 아닙니다). 실행이 끝나면 실제 비용을 메시지에 적습니다. 시험 수집도 크레딧이 들어서 한 번 더 묻습니다.
- **지킬 것:** 토큰은 환경 변수 `BYORBIT_APIFY_TOKEN`에만 넣습니다. 앱은 robots.txt 존중 옵션을 반드시 켜서 보냅니다(액터 기본값은 꺼짐).
- **솔직한 한계:** 이 앱의 Apify 방식은 실제 토큰으로 확인하지 못했습니다. 공식 문서와 가짜 응답으로만 시험했습니다. 처음 쓸 때 비용 상한을 작게 둡니다.

### 밖으로 나가는 것과 한계

수집할 때 밖으로 나가는 것은 **검색어와 그 출처의 API 키뿐**입니다. 자료함·CoA·시료·실험 데이터는 어떤 출처에도 보내지 않습니다.

한계도 솔직하게 적어 둡니다.

- OpenAlex는 키 없이 하루 약 100회까지 씁니다. Semantic Scholar는 키가 없으면 자주 잠시 막힙니다.
- 국내·키 필요 API 7개 중 6개는 실제 키로 아직 확인하지 못했습니다. 키를 받으면 첫 검색 결과를 꼭 눈으로 확인하세요.
- Apify 방식은 실제 토큰으로 확인하지 못했습니다. 처음 쓸 때 비용 상한을 작게 둡니다.

### 처음 쓸 때 자주 하는 실수

- **한 번에 너무 넓게 찾기** — "apple"처럼 넓은 검색어는 수백 건이 쌓입니다. "apple pomace drying"처럼 대상·주제를 함께 씁니다.
- **수집함을 그대로 자료함에 넣기** — 수집함은 후보입니다. 제목·초록을 보고 고른 것만 넣어야 검색과 AI 답이 깨끗합니다.
- **크롤러 간격을 줄이기** — 빨리 모으려고 간격을 줄이면 사이트에 부담을 주고 막힐 수 있습니다. 앱은 3초보다 짧게 줄이지 못하게 해 두었습니다.
- **키를 메신저로 주고받기** — 키는 각자 발급받아 자기 PC의 환경 변수에 넣습니다.

### 모은 기록은 어디에 남나

수집 화면 오른쪽 아래의 **최근 수집 기록**에 검색마다 몇 건이 새로 들어왔고 몇 건이 중복으로 합쳐졌는지, 어느 출처가 실패했는지가 남습니다. 수집함의 항목은 자료함에 넣기 전까지 따로 보관되고, 거절한 항목도 지워지지 않고 "거절" 탭에 남아 같은 자료가 다시 들어와도 또 검토하지 않게 해 줍니다. 자료함에 넣은 자료에는 출처(어느 API·사이트에서 왔는지)와 DOI·라이선스가 함께 기록되어, 나중에 인용할 때 그대로 씁니다.

저장 검색은 앱이 켜져 있는 동안에만 돕니다. PC를 끄면 멈췄다가, 다시 켜면 다음 예정 시각에 이어서 찾습니다. 저장 검색 카드의 **자동 실행 멈춤**으로 잠시 모두 멈출 수도 있습니다.

수집은 "많이 모으기"보다 "믿을 만한 것을 골라 넣기"가 목적입니다. 한 주에 한 번 수집함을 열어 새 항목을 훑고, 맞는 것만 자료함에 넣는 정도면 충분합니다. 그렇게 쌓인 자료가 검색·AI 답·지식그래프를 모두 더 정확하게 만듭니다.

반대로 근거가 약한 자료가 많이 섞이면, 검색 결과가 길어지고 AI 답에도 흐린 근거가 붙습니다. 그래서 이 앱은 자동 수집 결과를 곧장 자료함에 넣지 않고, 늘 사람이 한 번 보고 넣도록 만들었습니다. 이것도 4장에서 본 "사람이 마지막에 확인한다"는 원칙을 그대로 따른 것입니다.

::: info 핵심 정리
- 공식 API(정확한 창구)와 크롤러(공개 웹 목록 읽기) 두 길로 모읍니다.
- 모은 것은 수집함에서 검토한 뒤 자료함에 넣고, 중복은 DOI·출처 번호·제목으로 합칩니다.
- 모으는 방법은 공식 API·직접 크롤러·Playwright·Apify 네 가지이고, 공식 API가 있으면 그것이 먼저입니다.
- 키는 환경 변수로만, 크롤러는 robots.txt·약관·저작권·개인정보·간격을 지킵니다.
- 밖으로 나가는 것은 검색어와 키뿐이고, 한 출처가 실패해도 다른 출처 결과는 들어옵니다. 실패한 출처는 잠시 뒤 다시 찾거나 저장 검색에 맡깁니다.
- 저장 검색은 앱이 켜져 있을 때만 돌고, 모은 기록은 최근 수집 기록에 남습니다.
- 넷 중 무엇을 쓰든, 모은 자료를 자료함에 넣는 마지막 결정은 사람이 합니다.
